# Private module corpus

This directory is the local mount point for a **private** repository of MyBible-format modules used for compatibility testing.

Only this README is tracked by `sola-study-bible`. Everything else in this directory is ignored by Git. Never commit modules, generated caches, user data, or private settings here.

## Why this exists

The public repository contains the application code, small synthetic test fixtures, and the two public sample modules under `data/`. Those public samples are enough for basic CI, but they cannot represent the variety of real MyBible modules.

A full corpus contains copyrighted translations, commentaries, dictionaries, and user data that must not be redistributed under the project's GPLv3 license. Keep that corpus in a private repository and clone it here for local testing.

The test harness lives in the public repository at `tests/private_modules/`, not inside this data directory. That way every contributor gets the same tests and can run them against their own licensed corpus.

## Setup

1. Create a private repository (for example `my-mybible-modules`) and put every module you use in the MyBible app into it. A flat layout or a `modules/` subdirectory both work.
2. Clone it into a subdirectory of this folder:

   ```bash
   git clone <your-private-repo-url> private_modules/<repo-name>
   ```

   Do not clone directly into `private_modules/` itself; this README lives here.
3. Do not add the private repository as a Git submodule. Clone it locally and keep it ignored.
4. If the corpus already exists elsewhere, point the tests at it with `SOLA_TEST_MODULES` instead of copying files.

## Layout

```text
private_modules/
├── README.md                    tracked by sola-study-bible
└── <your-private-repo>/         ignored, local only
    ├── KJV+.SQLite3
    ├── Strong.dictionary.SQLite3
    ├── DV-c.commentaries.SQLite3
    ├── ...
    ├── ReferenceData.SQLite3    runtime-generated; not a module
    └── user/                    themes, fonts, bookmarks, settings
```

A `modules/` subdirectory inside the private repository is also supported. The harness scans recursively, skipping `.git/`, `user/`, `runtime/`, and hidden directories.

## Run the tests

From the repository root:

```bash
python -m pytest tests/private_modules -v
```

The harness auto-detects a single repository under `private_modules/`. If there is more than one, be explicit:

```bash
SOLA_TEST_MODULES="$PWD/private_modules/<repo-name>" \
  python -m pytest tests/private_modules -v
```

If no private corpus is present, these tests skip. A skip means **module compatibility was not tested**; it does not mean every module passed.

Run the public repository-hygiene test before committing:

```bash
python -m pytest tests/test_repo_hygiene.py -v
```

## What is checked

- Every real `.SQLite3` module opens read-only through a percent-encoded SQLite URI.
- Every module has an `INFO` table with a non-empty `description`.
- Bible modules have `VERSES`, `BOOKS` or `BOOKS_ALL`, and the required verse columns.
- Dictionary modules have either `DICTIONARY` or `WORDS` with the required columns.
- Commentary modules have `COMMENTARIES` with the required position and text columns.
- Subheading modules have `SUBHEADINGS` with the required columns.
- Cross-reference modules have `CROSS_REFERENCES` with the required columns.
- Reading-plan modules have `READING_PLAN` with the required columns.
- Devotion modules have `DEVOTIONS` with the required columns.
- `ReferenceData.SQLite3` is readable but is **not** classified as a module.
- Generated files such as `-*.cache.SQLite3`, `*.SQLite3.search`, `*.SQLite3.new`, `*-journal`, `*-wal`, and `*-shm` are not discovered as modules.
- Filenames containing apostrophes, plus signs, spaces, and non-ASCII characters remain addressable.

The tests do not assert exact article text or verse wording. That keeps them portable across translations and avoids copying copyrighted content into logs or reports.

## Runtime and user data

`ReferenceData.SQLite3` is generated by the reference application at runtime. The new application may read a compatible cache or generate its own; it is not a source module and is never treated as one.

`user/` contains themes, fonts, bookmarks, notes, and settings. It is useful for later theme/font/bookmark import tests, but it is not part of module discovery.

Do not commit proprietary fonts. For example, `user/fonts/Tahoma.ttf` is a proprietary Microsoft font and must not be redistributed in either repository. Use a system-installed font or an open-licensed font for tests; the application can still load user fonts at runtime.

## For an AI agent

If you are an AI agent working in this repository:

1. Work from the repository root.
2. Run `python -m pytest tests/private_modules -v`.
3. If the result says no private corpus is available, do not claim that module compatibility was tested. Report that the corpus is absent and run the public tests instead.
4. If multiple repositories exist under `private_modules/`, set `SOLA_TEST_MODULES` to the intended corpus root and rerun.
5. Never modify, delete, move, or write to files under `private_modules/`. All module access is read-only.
6. Never run `git add`, `git commit`, or `git push` on anything under `private_modules/`. Only `private_modules/README.md` is tracked.
7. Before committing, run `python -m pytest tests/test_repo_hygiene.py -v` and `git status --short`. If a module file appears as staged or tracked, stop and report it.
8. If a module fails, report its relative filename, detected type, and exception. Do not "fix" the corpus by deleting the module.
9. Do not paste article text, verse text, dictionary definitions, or other module content into commits, issues, logs, or public artifacts.
10. Do not add the private corpus as a submodule or remote of the public repository.

## Licensing

The modules are data with their own copyright and license terms. The application is GPLv3, but that does not relicense the modules. Keep this corpus private, limit access to people entitled to use those modules, and never include it in a public release, source archive, container, or CI artifact.

A private GitHub repository is still distribution to anyone invited to it. If another contributor needs to test modules, they should use their own licensed corpus with `SOLA_TEST_MODULES`; the public tests and fixtures must remain sufficient for normal development.

## Temporary status

These tests are a standalone corpus audit until the application data layer exists. Once `sola.data` is implemented, the tests should call the same discovery and query APIs as the application while preserving the read-only rule and this corpus layout.
